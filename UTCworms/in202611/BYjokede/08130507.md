## Buzz (from A unless marked B)

1. Identity. Each agent has its own Nostr keypair, generated with
   buzz-admin generate-key (crates/buzz-acp/README.md). The relay never
   holds agent keys. The agent process gets its key as BUZZ_PRIVATE_KEY.
2. Owner attestation. NIP-OA (docs/nips/NIP-OA.md): an owner-signed auth
   tag on an agent's events. NIP-AA (docs/nips/NIP-AA.md): an agent whose
   owner is a relay member may get implicit relay access by presenting it.
   Production compose sets BUZZ_ALLOW_NIP_OA_AUTH=true. Both are Block-only
   drafts; an unrelated upstream proposal is also called NIP-AA (B).
3. Membership. NIP-43 when BUZZ_REQUIRE_RELAY_MEMBERSHIP=true. Managed with
   buzz-admin add-member --pubkey npub... [--role admin], or kinds
   9030/9031/9032 sent by owner or admin. The admin UI covers moderation
   only. NIP-46 bunkers are out of scope.
4. Channels are NIP-29 groups (NOSTR.md). Types: Stream, Forum, Dm,
   Workflow, System. Any member may create one (kind 9007, or buzz channels
   create); the creator owns it. Options: open or private, unlisted, TTL,
   guest-only posting, auto-join. Threads are NIP-10 replies; there are no
   sub-channels. NIP-CL tags help agents find channels they created.
5. Granularity. The vision docs describe a channel per branch, archived on
   merge (VISION_PROJECTS.md). Buzz gives an agent a separate session per
   channel, and a membership change starts a fresh session (B, citing
   docs/practical-information-flow-for-buzz-agents.md).
6. Agent runtime. buzz-acp runs goose, codex-acp, claude-agent-acp or the
   in-repo buzz-agent when @mentioned. buzz-agent supports anthropic,
   openai, openrouter and databricks. Caps are per turn only
   (BUZZ_AGENT_MAX_ROUNDS, max output tokens, timeouts). No spend budget,
   and rate limiting is not enforced (ARCHITECTURE.md).
7. Known gap (B): block/buzz issue #9207, opened 2026-11-06. A provider
   quota or billing error (429/402) is retried for about 25 minutes, then
   the message is dropped without telling its author.
8. Workflows: channel-scoped YAML, triggered by message, reaction, diff,
   schedule or webhook (POST /hooks/{id}). The webhook secret is a plain
   shared secret, not HMAC, so GitHub's signed webhooks are not verified
   natively. Approval gates are not finished yet.
9. Git.
   a. A repo is announced with NIP-34 kind 30617 (buzz repos create). It
      must carry a buzz-channel tag; unbound repos 404 except to their
      author.
   b. Reads need membership of the bound channel. Pushes go through a
      pre-receive hook using channel roles: members and bots may push,
      guests may not. Agents inherit access through NIP-OA.
   c. Auth: git-credential-nostr (NIP-98, needs git 2.46+);
      git-sign-nostr signs commits.
   d. No GitHub mirroring or import, documented or in the code.
   e. (B) says the object-storage code sits on an unmerged PR (#726). The
      README marks git hosting as working and our relay answers, so treat
      it as live but young.
10. The three variables in issue #2 (from the source):
    a. BUZZ_GIT_CONFORMANCE_PROBE, default true: an S3 race test at
       startup; failure is fatal.
    b. BUZZ_GIT_HOOK_HMAC_SECRET: an HMAC key for the hook's callback to an
       internal policy endpoint. Random if unset; must be set, at least 32
       characters, with more than one replica.
    c. BUZZ_GIT_REPO_PATH, default ./repos: scratch and pack cache only.
11. Maturity. The README says "Not finished". There are about 512 commits
    in the last 30 days and 69 authors in 3 months. Tags include v0.5.2,
    relay-v0.2.1 and desktop-v0.5.28. Launched 2026-07-21 (B, secondary
    sources).

## Existing practice (B)

1. Issue-driven agents: the Copilot coding agent, the Claude Code GitHub
   Action and OpenHands all use one issue = one session = one branch = one
   PR. None commits straight to main. Caps come from turns or iterations
   plus provider budgets (Claude Code: --max-turns, --max-budget-usd).
2. Channel per issue: Rust's triagebot opens a Zulip topic per issue, and
   incident tools open a channel per incident with one central feed. The
   cost is sprawl, which the central feed offsets.
3. Git on Nostr: ngit v3 (2026-09) with GitWorkshop and GRASP servers is
   the most mature stack. It is separate from Buzz's own git hosting. No
   maintained tool mirrors GitHub issues into NIP-34.
4. Agents on Nostr: NIP-90 is now "draft unrecommended". Agent identity is
   not standardised upstream (many proposals, none merged).

## What this implies for us (provisional)

1. A channel per issue, plus one feed channel for the repo.
2. The repo must be bound to a channel, so the feed channel is also the
   repo's channel.
3. Per-session bee keys, vouched for by the owner through NIP-OA.
4. Budget is ours to enforce: one session per issue with a spend cap.
5. A GitHub-to-relay link is ours to build: push main to both.
